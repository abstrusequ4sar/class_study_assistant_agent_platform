# 课程学习助手 Agent 平台逐页演讲稿

适用文件：`课程学习助手Agent平台新版汇报.pptx`

汇报方式：一人连续讲解全部 24 页

建议时长：约 14—16 分钟，现场操作演示时间另计

## 第 1 页：课程学习助手 Agent 平台

建议用时：25 秒

各位老师好，我汇报的项目是“课程学习助手 Agent 平台”。它面向大学生的多课程学习场景，把课程资料管理、资料检索、智能问答、学习计划和待办任务整合在同一个平台中。这个项目的核心不是增加一个普通聊天框，而是让 Agent 能够基于真实课程资料作答、给出可核查来源，并把学习目标转化为可执行的计划和任务。

接下来我会按照“为什么做、系统怎样设计、每项功能如何实现、项目有哪些优势”的顺序进行介绍。

## 第 2 页：为什么做——学习问题不是“缺一个聊天框”

建议用时：35 秒

项目来自四个常见问题。第一，课件、笔记、作业和实验文档分散在不同位置；第二，资料变多以后，靠文件名很难快速找到具体知识点；第三，“两周复习完”这类目标缺少阶段和每日安排；第四，作业、实验和复习任务很容易遗漏。

所以我们要解决的不是单独的问答问题，而是把资料、知识和行动连接起来，让学生能从“资料在哪里”一直走到“今天具体做什么”。

## 第 3 页：项目目标——建立以课程为中心的学习闭环

建议用时：35 秒

系统以课程作为核心边界。资料上传后先进行内容抽取和检索，Agent 再基于检索结果回答问题或生成计划；计划中的每日安排会继续转成待办任务，任务完成情况又能反映学习进度。

对学生来说，它把“找文件”变成“找答案”，把“有目标”变成“今天做什么”；对工程实现来说，业务接口和 Agent 工具复用同一套权限与数据逻辑，并且在外部模型不可用时仍保留基础功能。

## 第 4 页：需求完成全景

建议用时：30 秒

这一页是原始需求的完成情况。用户认证、课程管理、资料管理、Agent 对话、学习计划、待办任务和个人中心等基本功能已经实现；来源引用与跳转、知识点整理、智能任务拆解和多课程规划等高级功能也全部完成。

此外，我们补充了 SSE 流式输出、双模型协议、离线降级、任务日历、到期提醒和 Markdown 安全消毒。每项需求都有对应的页面、API、数据结构和测试，不只是界面展示。

## 第 5 页：系统总体架构

建议用时：45 秒

系统采用前后端分离架构。表现层使用 Vue 3、Element Plus、Pinia 和 Vue Router，负责页面交互与登录状态；API 层使用 FastAPI，按认证、课程、资料、对话、计划和任务划分路由。

业务服务层包括 Agent 循环、统一 LLM 客户端、资料检索、文件解析、Embedding 和安全服务。底层用 SQLAlchemy 管理 SQLite 数据库，原始文件单独保存在上传目录，模型则可以接入 Anthropic 或 OpenAI 兼容服务。

这种分层的优势是模型、检索方式和数据库都可以替换，同时普通 API 与 Agent 工具能够复用后端权限逻辑。

## 第 6 页：核心数据与学习闭环

建议用时：40 秒

系统共有 8 张主要业务表。User 和 Course 确定用户与课程边界；Material 和 MaterialChunk 保存原始资料及切片；Conversation、Message 和引用快照保存对话证据；StudyPlan 和 Task 保存计划与执行结果。

完整数据流是：上传资料、抽取切片、检索引用、Agent 决策、计划或任务落库，最后进入日历跟踪。这样，智能回答和学习计划都不是一次性文本，而是可以追溯、修改和继续使用的数据。

## 第 7 页：用户认证

建议用时：30 秒

学习资料、对话和计划都属于个人数据，因此系统首先建立用户身份边界。密码使用 PBKDF2 加盐哈希保存，登录成功后由带过期时间的 JWT 维持会话；前端路由守卫会拦截未登录访问，页面刷新后 Pinia 通过 `/auth/me` 恢复用户信息。

更重要的是，权限不是只靠前端隐藏按钮，而是所有业务接口都重新获取当前用户并检查对象归属。

## 第 8 页：个人中心

建议用时：25 秒

个人中心把分散在不同模块中的学习数据汇总起来。页面并行获取课程、学习计划、未完成任务和对话数量，展示统计卡片、最近对话和快捷入口，同时支持修改昵称和密码。

这里没有额外建立重复的统计后端，而是复用已有 RESTful API，在前端完成数据汇总，减少了接口冗余。

## 第 9 页：课程管理

建议用时：30 秒

多门课程必须有清晰边界，因此课程信息包含名称、简介、授课教师和学期，并提供完整的新增、查看、修改和删除功能。前端使用响应式卡片展示课程，也能直接进入对应课程的 Agent 问答。

后端通过课程所有者进行数据隔离。资料、对话和计划在继续访问前都会回到课程归属进行校验，不同用户即使猜到对象 ID，也无法读取他人的课程数据。

## 第 10 页：课程资料管理

建议用时：45 秒

这一页展示最新的资料上传机制。用户可以把多个课程文件直接拖入上传区域，也可以点击选择文件；单批最多 10 个，单个文件默认限制为 50MB。前端会过滤空文件和重复文件，并显示待上传数量、总大小和当前进度。

批量上传时，成功文件会自动移出队列，失败文件会保留，用户可以直接重试。后端把原文件存入受控目录，把文件名、类型、说明和大小写入 materials 表。页面下方同时提供分类筛选、下载、删除和正文检索，因此资料归档与内容查找集中在同一处。

## 第 11 页：多格式解析与资料检索

建议用时：45 秒

通用模型本身不知道学生上传的课程资料，所以文件入库后还要经过解析。系统支持文本、Markdown、PDF、DOCX 和 PPTX，抽取正文后按照 600 字、重叠 100 字进行切片，尽量避免知识点在切片边界被截断。

配置 Embedding 时，系统使用向量余弦相似度进行语义检索；未配置或调用失败时自动退回关键词打分。每个命中结果保留资料 ID 和切片 ID，既能处理同义表达，也能为后续来源引用建立追溯依据。

## 第 12 页：完整工具驱动 Agent 对话

建议用时：60 秒

这是项目的核心。固定 RAG 通常只检索一次再作答，资料不足时不能主动换关键词，也不能执行任务。我们的实现会向模型提供资料、课程、任务和计划共 10 个工具。模型可以自主决定调用哪个工具、调用几轮以及什么时候结束，后端最多允许 8 轮，防止异常循环。

每次工具请求都由后端执行真实查询或写入，并再次检查当前用户权限。SSE 会把元信息、工具事件、增量文本和最终引用实时发送到前端，所以用户能看到 Agent 做了什么，而不只是最后一段回答。

流式和非流式消息接口现在复用同一套完整 Agent 循环，两者只在返回方式上不同；Anthropic 与 OpenAI 兼容协议也复用同一套业务工具。

## 第 13 页：资料来源展示

建议用时：45 秒

基于私有资料回答时，最重要的是结果能否核查。Agent 多轮检索可能重复命中同一片段，因此系统用 chunk_id 去重，在一次对话过程中为片段分配稳定编号。模型看到的工具结果包含编号，最终回答中的 `[1]`、`[2]` 就能与前端来源标签一一对应。

每条引用会保存资料 ID、资料名称和原文摘录，前端可以悬停查看，历史消息也保留当时的引用快照。这样，来源不是模型临时编造的脚注，而是后端检索结果形成的证据。

## 第 14 页：资料来源点击跳转

建议用时：35 秒

只显示资料名称还不够，因为用户仍然需要重新查找原文件。所以来源标签现在支持鼠标点击和键盘 Enter 跳转。前端把 material_id 和引用编号写入路由查询参数，课程资料页读取参数后定位对应资料，并用提示条、蓝色背景和左边框高亮目标行。

用户从回答到来源只需一次点击，之后可以下载原文或继续检索资料内容，完成了“回答、证据、原始文件”之间的闭环。

## 第 15 页：知识点整理

建议用时：35 秒

资料已经归档，并不代表已经形成适合复习的知识结构。知识点整理现在会读取课程内全部可解析切片，不再只截取前 30 个。系统从文件名或正文识别 Chap、Chapter 和“第 N 章”等章节号，资料之间按自然章节顺序排列，同一资料内部严格保持原文顺序。

排序后的内容按最多 50 个切片或约 30000 字符分批，后端最多同时处理 3 批，并按照预先记录的位置组合，因此提速不会打乱顺序。专用 SSE 接口会立即告诉前端资料数、片段数和总批次数，随后实时更新进度条和耗时；没有配置模型时，系统仍按章节顺序返回全部资料片段目录。

## 第 16 页：单课程学习计划

建议用时：40 秒

“两周复习完高等数学”仍然是一个过大的目标。用户输入课程、学习目标、截止日期和每日可用时长后，计划服务会生成 overview、stages 和 daily_tasks 三部分结构化数据。

后端使用 Pydantic 校验日期、时长和任务数量，计划保存以后，再把每日任务批量写入待办列表。这样生成的不是一段只能阅读的建议，而是可以编辑、完成和跟踪的真实计划。没有模型时，也可以按照日期和时长规则生成确定性的基础计划。

## 第 17 页：智能任务拆解

建议用时：40 秒

智能任务拆解把宏观目标逐步转化为可执行动作。模型先返回结构化 JSON，后端再进行 Schema 校验和日期归一化，保存 StudyPlan，并批量生成 Task。

阶段任务用于表达复习方向，每日任务用于表达当天可以完成的具体动作；每条任务保留课程、计划和截止日期关联。系统单次最多生成 60 条待办，避免异常输出。Agent 在对话中也可以调用创建计划或创建任务工具，把自然语言指令直接变成真实数据。

## 第 18 页：多课程综合学习规划

建议用时：40 秒

当多门课程同时有截止日期时，分别规划容易发生时间冲突。多课程规划一次接收多组课程、目标和期限，以及每日总可用时长，让计划服务在统一时间预算下分配任务。

每条每日任务都必须返回课程归属，后端还会校验课程 ID 属于当前用户，并且确实在本次规划请求中。生成后的任务可以在任务页按课程筛选。离线模式下，系统会根据课程数量和剩余日期平均分配学习时间。

## 第 19 页：待办任务、日历与到期提醒

建议用时：35 秒

系统中的任务有三种来源：用户手动创建、学习计划自动生成，以及 Agent 在对话中创建。它们统一进入同一套任务数据和状态规则，支持增删改查、完成勾选和课程筛选。

列表视图按紧急程度排序，日历视图按日期展示。提醒接口会把未完成任务划分为已逾期、今天到期和三日内到期，登录后给出全局提醒。这样，计划最终落实到了每天可以检查和完成的安排中。

## 第 20 页：RESTful API 与数据存储

建议用时：40 秒

后端按照认证、课程、资料、对话、计划和任务划分 RESTful 路由，共提供 34 个 OpenAPI 操作，并自动生成 Swagger 文档。FastAPI 路由层负责身份依赖、参数校验和响应模型，SQLAlchemy 负责数据关系，Pydantic 负责请求与响应结构。

文件本体与 SQLite 元数据分离存储，数据库地址可以通过 DATABASE_URL 替换。路由、Schema、ORM 和服务层相互分离，所以增加新功能时不需要修改无关模块；普通消息和 SSE 消息也共用完整 Agent 入口。

## 第 21 页：可用性、安全与降级设计

建议用时：40 秒

安全方面，系统对课程、资料、对话和任务逐次校验归属；密码使用加盐哈希，JWT 带签名和过期时间；上传限制大小并净化文件名，下载前再次检查权限；模型返回的 Markdown 经过 DOMPurify，过滤危险标签、事件和 URL。

可用性方面，AI 被设计为可选增强，而不是基础业务的单点依赖。没有 LLM 时，问答可以返回检索片段，计划可以使用确定性规则；Embedding 不可用时，检索自动切换到关键词模式。因此外部服务异常不会让课程、资料和任务功能整体失效。

## 第 22 页：测试覆盖与验证结果

建议用时：35 秒

项目通过了 45 项后端 pytest、2 项前端安全渲染测试和 Vite 生产构建，依赖审计未发现已知漏洞。测试覆盖的不只是普通 CRUD，还包括两个用户之间的数据隔离、DOCX 与 PPTX 解析、知识点全切片覆盖、章节排序、三批并发与 SSE 进度，以及 OpenAI 和 Anthropic 两种工具协议。

测试使用模拟模型客户端验证协议和工具循环，不会消耗真实 API 额度，因此可以稳定重复执行。

## 第 23 页：项目亮点与实际优势

建议用时：40 秒

项目可以总结为五个亮点。第一，Agent 可执行，不只回答问题，还能检索资料、查询任务、创建任务和保存计划；第二，来源可核查，具有稳定编号、片段摘录、历史快照和点击跳转；第三，模型可替换，统一支持 Anthropic 与 OpenAI 兼容协议；第四，在线和离线模式统一，外部服务失败仍能运行基础业务；第五，资料、问答、计划、任务和反馈形成完整学习闭环。

这些亮点共同解决了普通聊天系统“不能执行、无法追溯、依赖外部服务”的问题。

## 第 24 页：总结与现场演示路线

建议用时：35 秒

最后总结一下，系统完成了从“管理学习资料”到“根据资料执行学习计划”的转变：Agent 的回答可以核查，学习计划可以落地，待办任务可以跟踪。

如果进行现场演示，我会依次展示登录和课程、拖拽上传并检索资料、Agent 多轮调用工具、点击来源跳转、生成多课程计划，以及在日历中跟踪任务。项目由三人共同完成；在人机分工上，人类负责基础规划与需求分析，AI 只负责明确要求下的细节代码填写，所有结果均由人类复核和测试。

## 现场演示备用提示

1. 优先演示“拖拽上传—Agent 提问—来源跳转”，这是最能体现项目闭环的路线。
2. 如果外部模型响应较慢，可以先展示历史对话中的工具事件和引用，再说明系统具备离线降级。
3. 如果时间不足，可简讲第 8、20、21 页，把时间留给第 10、12、13、14、17 和 19 页。
4. 现场操作前检查后端 8000 端口、前端 5173 端口和登录状态，准备一个体积较小的 Markdown 或 PDF 作为拖拽示例。
